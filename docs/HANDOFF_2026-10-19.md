## 2. 사용자의 의도와 지켜야 할 구분

사용자는 검색 결과도 공모전 추가 탐지 결과에 포함되어야 한다고 지적했다. 예시는 다음과 같다.

- URL 검색 파라미터에 광고가 삽입되어 구글에 노출됨.
- 게시판 광고 글은 삭제됐지만 구글의 제목·요약에는 광고가 계속 노출됨.
- 현재 게시글에도 광고가 있고 검색에도 색인되어 노출됨.

현재 사이트에 광고가 존재하는지와 검색 결과에 광고가 노출되는지는 별도 상태다. HTTP 403, 타임아웃, 네트워크 오류를 삭제로 판정해서는 안 된다. URL에 검색 단어가 있다는 사실만으로 광고 노출을 확정해서도 안 된다.

사용자에게는 처음 `results.json`을 설명하면서 제출 연계 누락을 충분히 짚지 못했다. 이후 다음으로 정리하고 구현했다.

| 파일 | 역할 |
|---|---|
| `result.json` | 필수 4종 탐지 결과, 적격평가용 |
| `result_extra.json` | 추가 유형 결과, 검색 노출 광고 포함, 본심사용 |
| `results.json` | 검색 후보·질의·진행 상태·상세 근거를 보존하는 내부 기록 |

`results.json` 자체가 금지된 파일이라는 뜻은 아니다. 제출용 추가 결과를 이 파일에만 보관하는 것이 문제였으며, 내부 상세 기록으로 유지하는 방식으로 개선했다.

## 3. 확인한 공모전 규격

저장소 루트의 `공공 웹사이트 불법광고 탐지 도구 개발 공모전 모집요강.pdf`를 pypdf로 추출하여 확인했다. 기준은 로컬 PDF이며 최신 외부 공지나 주최 측 유권해석까지 확인한 것은 아니다.

- 5·9쪽: 필수 4종은 `result.json`, 추가 개발 유형은 `result_extra.json`으로 분리.
- 9쪽: 실행 파일 위치에 저장하는 것이 원칙. 다른 위치이면 사용설명서 첫 장에 파일별 경로를 명시.
- 10쪽: UTF-8, BOM 없음, 최상위 `meta`와 `findings` 두 키, 0건도 `findings: []` 포함.
- 10쪽: 검출 단위는 `url + location + technique`. 복수 기법은 별도 객체로 기록.
- 10~11쪽: `meta.topic`, `entry_url`, `started_at`, `finished_at`, `elapsed_sec`; `tool_version` 선택.
- 11쪽: findings에 `id`, `url`, `is_violation`, `location`, `evidence_text`, `technique`.
- 추가 유형은 `technique: "ETC"`, 구체적 유형은 `extra_finding`.
- 위치는 CSS 선택자가 원칙이며 동일 요소를 정확히 가리키는 다른 표기도 인정한다는 설명이 있다.
- 13~14쪽에 일반·추가·0건 예시가 있다.

주의: 검색 API 결과의 서술형 위치 표기를 주최 측이 인정하는지, 검색 이후 합본 시간 구간이 평가 의도에 맞는지는 별도 확인이 필요하다. 로컬 스키마 통과가 모든 공모전 요건 충족이나 수상 가능성 검증을 의미하지 않는다.

## 5. 검색 제출 JSON 구현 상세

### 데이터 흐름

```text
SerpApi / browser 수집
  → search_discovery.save(run, folder)
      → results.json / urls.txt / review.csv / report.html
      → search_submission.export()
          → 해당 폴더/result_extra.json

GUI SearchJob._work() 또는 CLI main() 완료·회수·재검사
  → search_submission.publish()
      → 출력 폴더/result_extra.json 병합
```

현재 GUI 기준 저장 위치:

```text
out/
  result.json                       # 기본 점검 파일: 검색 코드에서 수정하지 않음
  result_extra.json                 # 같은 호스트이면 기존 추가 결과 + 검색 결과
  search_results/<실행폴더>/
    result_extra.json               # 이 검색 실행의 제출용 파일
    results.json                    # 내부 상세 기록
    urls.txt
    review.csv
    report.html
    google/ 또는 naver/             # 엔진별 기록·증거 및 제출 파일
```

### `document(run)`

- 제목 + 줄바꿈 + 요약을 기존 `findings.classify()`에 전달한다.
- 광고로 판정된 검색 출처만 제출 대상으로 삼는다. 정상·미확인 후보 전체는 내부 `results.json`에 남는다.
- 범위 밖 URL은 제외한다. 기존 `target_host()`·`in_scope()`를 재사용한다.
- URL 파라미터 값도 `classify()`로 검사한다. 단순 검색어 일치는 제출 기준으로 쓰지 않는다.
- `is_violation: true`는 검색 노출 광고 판정이다. 현재 페이지 광고 존재를 뜻하지 않는다.
- `evidence_text`: 제목·요약 원문, 검색 시각, 현재 검사 상태·HTTP·시각·설명, 광고 파라미터, 현재 페이지 검출 근거.
- `location`: 검색엔진·검색 URL·검색 페이지 번호·대상 링크를 포함한 서술 문자열. API에 없는 CSS 선택자는 생성하지 않는다.
- 실행별 중복 키는 `(url, location)`이며 `technique`은 모두 ETC다.

추가 유형은 아래 순서로 선택된다.

| 우선순위 | 코드 | 조건 |
|---|---|---|
| 1 | `SEARCH_REMOVED_AD` | 현재 HTTP 404·410 |
| 2 | `SEARCH_PARAMETER_AD` | 광고로 판정된 URL 파라미터가 있음 |
| 3 | `SEARCH_LIVE_AD` | 현재 findings가 있고 상태가 `확인 불가`가 아님 |
| 4 | `SEARCH_INDEXED_AD` | 그 외 검색 제목·요약의 광고 노출 |

이 코드들은 이번 프로젝트가 정한 추가 유형명이다. 기존 `index_check.py`의 `SEARCH_INDEXED`는 Search Console 등 사용자가 제공한 색인 URL 목록 검사이며 별개다.

404·410은 현재 URL의 삭제 응답이지 과거 게시글 존재·삭제 원인까지 입증하는 것은 아니다. HTTP 200의 삭제 안내는 `삭제 안내 의심`으로 근거에 남기며 REMOVED로 분류하지 않는다.

### `publish(run, folder, output)`

- 실행별 제출 파일은 먼저 보존한다.
- 기존 출력 파일은 JSON 파싱·스키마 검사를 거친다. 오류이면 원본을 덮어쓰지 않는다.
- 기존 meta.entry_url과 새 결과의 netloc가 다르면 합치지 않고 실행별 제출 파일 경로를 로그로 안내한다.
- ID 접두사는 실행 폴더 절대 경로의 SHA-256 앞 16자리로 만든다.
- 같은 실행을 회수·재검사하면 해당 접두사 항목을 지우고 새 결과로 교체한다.
- 다른 검색 실행에서 같은 `(url, location, technique)`을 재확인한 경우 이전 검색 항목을 최신 근거로 교체한다.
- 기존 기본 추가 결과는 보존한다. 기본 `result.json`과 기본 실행 아카이브는 수정하지 않는다.
- 합본 meta 시간은 최초 시작~최종 종료 사이의 경과 시간으로, 사이의 대기도 포함한다.
- CLI `--out`은 검색 저장 루트이며 합본은 `args.out.parent`에 생성한다. `--input`과 `--resume-search`도 동일하다.

## 6. Kakao 제거 내용

- 화면의 Daum 체크박스와 Kakao 상태 안내 제거.
- GUI·API·브라우저 수집의 지원 엔진은 Google·Naver만 허용.
- Kakao 연결 확인 및 검색 HTTP 호출 코드 제거.
- `load_keys()`는 `SERPAPI_API_KEY`만 반환한다. 환경변수·파일에 옛 Kakao 키가 있어도 사용하지 않는다.
- 키 예시·dork 설정·사용법도 정리했다.
- `hybrid` 옵션은 호환성을 위해 유지하지만 지원하는 두 엔진 모두 API 경로를 사용한다. `browser`는 별도 선택 가능.
- `link_check.py`의 `kakao.com`, `daum.net`은 일반 외부 링크 분류용 플랫폼 목록이므로 삭제하지 않았다. 검색 API 코드와 무관하다.
- 실제 `search.env`에 Kakao 설정이 있을 경우 해당 줄만 제거하는 처리를 실행했으나 변경 메시지가 없었다. 실제 파일 내용이나 키 값은 출력하지 않았다.

## 7. 키 입력 UI 및 서버 계약

오른쪽 위 **검색 API** → **검색 API 설정**.

- 입력은 기본 password 마스킹.
- 보기/숨기기는 현재 입력 중인 키만 전환한다.
- 저장 및 연결 확인: POST 저장 성공 후 입력란을 비우고 계정 조회로 연결·잔여 검색량 확인.
- 키 삭제: 파일의 SerpApi 키 설정만 제거, 나머지 설정·주석 보존.
- 닫기·저장 처리 후 입력란을 비우고 password로 복귀.
- 기존 키는 GET 응답으로 내려보내지 않는다. 등록 여부만 표시.
- 저장되었으나 인증 실패·네트워크 실패이면 ‘저장됨’과 ‘연결 실패’를 구분한다.

### 엔드포인트

```text
GET /api/search/key
  → {registered: boolean, environment: boolean}
  Cache-Control: no-store

POST /api/search/key
  body: {action: "save", key: "새 키"}
     또는 {action: "delete"}
  → 동일한 등록 상태만 반환, 키 반환 없음
```

- POST는 `Origin: http://127.0.0.1:<실제 서버 포트>` 및 `Content-Type: application/json`을 요구한다.
- 외부 Origin 또는 Origin 없는 요청은 403.
- 점검·조치 재검사·검색 진행 중이면 409.
- 잘못된 action·입력·환경변수 우선 상황은 400, 파일 저장 실패는 키를 포함하지 않는 일반 오류로 500.
- `store_key()`는 영문·숫자·밑줄·하이픈 8~512자만 허용한다.
- 같은 폴더 임시 파일에 기록·flush·fsync 후 `os.replace()`로 교체한다. 정상적인 실패 경로에서는 임시 파일을 정리한다.
- 삭제는 `store_key(path, None)`이다. 파일 자체를 삭제하지 않고 SerpApi 설정만 제거한다.
- `SearchJob.health_lock`으로 저장/상태 읽기/연결 캐시를 조정하고 저장 시 캐시를 비운다.
- 환경변수 `SERPAPI_API_KEY`가 파일보다 우선한다. 값이 있으면 화면 수정·삭제를 막고 환경변수 해제 후 재시작을 안내한다.
- 저장은 `search.env` 평문 파일이다. 암호화 저장소·Windows 자격증명 관리자 구현은 없다. 문서에 명시했다.
- 원자적 교체는 파일 보존 장치이지 디스크 암호화나 악성 로컬 프로세스 방어를 뜻하지 않는다.

## 9. 실행·재시작 방법

```powershell
# 일반 실행
.venv\Scripts\python detector\main.py --out out

# 브라우저를 자동으로 띄우지 않는 서버 실행
.venv\Scripts\python detector\main.py --no-browser --out out
```

가상환경에 의존성을 다시 설치해야 하면 현재 확인된 방법:

```powershell
python -m pip --python .venv\Scripts\python.exe install --require-hashes -r requirements.lock
```

`playwright install`은 필요 없다. 탐지는 시스템 Edge를 사용한다. 선택 OCR용 winrt 패키지는 이번 작업에서 설치하지 않았다.

재시작 전 `/api/status`의 `running`, `rechecking`과 `/api/search/status`의 `running`을 확인한다. 진행 중이면 임의 종료하지 않는다. 키 상태·검색 상태 API의 전체 내용을 출력할 필요 없이 필요한 불리언만 확인한다.

```powershell
$guiStatus = Invoke-RestMethod 'http://127.0.0.1:8900/api/status'
$searchStatus = Invoke-RestMethod 'http://127.0.0.1:8900/api/search/status'
if ($guiStatus.running -or $guiStatus.rechecking -or $searchStatus.running) {
    throw '작업 진행 중: 재시작 보류'
}
Invoke-RestMethod 'http://127.0.0.1:8900/api/quit' -Method Post -ContentType 'application/json' -Body '{}'
```

종료를 확인한 뒤 프로젝트 폴더에서:

```powershell
$guiPython = Join-Path (Get-Location) '.venv\Scripts\python.exe'
Start-Process -FilePath $guiPython `
    -ArgumentList 'detector\main.py --no-browser --out out' `
    -WorkingDirectory (Get-Location).Path -WindowStyle Hidden `
    -RedirectStandardOutput 'gui.stdout.log' -RedirectStandardError 'gui.stderr.log'
```

페이지 새로고침 후 오른쪽 위 검색 API 창을 열면 된다. 키 설정 저장 후에는 서버 재시작이 필요 없다.

## 10. 후속 검토 사항 — 해결됐다고 가정하지 말 것

다음은 인계 시 코드 검토로 확인한 제한 또는 잠재적 개선점이다. 별도 검증·수정은 이번 인계 작성에서 수행하지 않았다.

1. **제출 위치 표현의 심사 인정 여부**: API 결과에 검색 DOM이 없어 `location`이 서술형이다. 일반 스키마 검사는 통과하지만 실제 공모전 추가 유형 심사 적합성은 주최 측 기준 확인이 필요하다.
2. **입력 URL·시간 의미**: 검색 실행 meta.entry_url은 target 호스트에 `https://`를 붙여 만든다. 원래 기본 점검의 경로·스킴을 유지하는 것은 합본 시 기존 meta가 있을 때다. 합본 시간은 기본 점검과 검색 사이 대기를 포함한다. 최초 입력 URL 및 평가 시간 정의를 더 엄밀히 연결하려면 실행 ID 기반 연계 설계를 검토한다.
3. **포트 처리**: publish는 netloc(포트 포함)를 비교하지만 기존 `target_host()`는 포트를 제거한다. 포트를 쓰는 localhost 점검과 검색 결과가 자동 병합되지 않을 수 있다. 현재는 실행별 제출 파일을 보존하고 로그로 안내한다.
4. **합본의 수명**: 새 기본 점검·지난 이력 열기 등으로 출력 폴더의 제출 사본이 교체될 수 있다. 검색별 제출 파일은 남지만 기본 실행 아카이브·SQLite 이력에는 검색 결과를 통합하지 않았다. 자동 재병합이나 실행별 연결은 아직 없다.
5. **현재 GUI 기본 결과 목록**: 검색 노출 항목은 검색 보고서 및 제출 JSON에 반영한다. 기본 점검 결과 테이블의 findings에 직접 주입하지 않는다.
6. **중복 교체와 과거 재회수**: 현재 폴더 접두사와 검색 위치 기준의 교체다. 새 실행 후 과거 실행을 다시 회수할 때 근거 시각을 비교하여 정말 최신인지를 보장하는 로직은 없다. 폴더 이동 시 ID 접두사가 바뀌는 점도 검토 대상이다.
7. **원본 메타 없는 이전 검색 기록**: started_at이 없으면 현재 시각을 사용한다. 과거 기록을 수동 변환할 때 실제 수행 시간을 복원하는 기능은 아니다. 중간 저장에는 완료 시각이 아직 없을 수 있다.
8. **저장 시각과 엄밀한 전체 소요 시간**: search_submission은 검색 run의 시각 문자열로 시간을 계산한다. 제출 JSON 최종 직렬화·디스크 저장 시간을 모두 계측하는 구조는 아니다.
9. **분류 한계**: 제목·요약을 기존 키워드 판정기로 판단하므로 오탐·미탐 가능성이 있다. 정상 안내/예방 기사에 대한 실검색 평가가 필요하다. 사용자에게 ‘확인’이라고 설명했지만 인간 검토를 완료했다는 뜻은 아니다.
10. **미지원 과거 엔진 회수**: 예전 Daum pending 검색 ID가 담긴 파일의 회수는 지원하지 않는다. 이 상황에 대한 전용 마이그레이션·안내 테스트는 없다.
11. **문서의 남은 모순**: 사용설명서 ‘상용 AI API 사용 여부’ 절 뒤에 ‘인터넷 연결은 점검 대상 누리집 접속 용도로만 사용’이라는 기존 문장이 남아 있다. 기본 탐지에 한정하도록 정리할 필요가 있다. 검색 API 도입 설명과 혼동될 수 있다.
12. **localhost 별칭**: 키 변경 Origin 검사는 `127.0.0.1`을 기준으로 한다. `http://localhost:8900`로 접근하면 변경 요청이 거절된다. 안내 주소를 사용하면 통과한다.
13. **보안 저장소 범위**: `search.env`는 평문이다. 파일 권한·Windows Credential Manager·강제 종료 직후 임시 파일 잔존까지 별도 보장하지 않는다. `.gitignore`만으로 비밀이 이미 추적된 상황을 해결하는 것은 아니다.
14. **병렬 CLI 실행**: GUI는 작업 상호 배제를 하지만 별도 CLI 프로세스 간 합본 파일 read-modify-write 잠금은 없다. 동시에 같은 출력 폴더에 게시하면 갱신 유실 가능성을 검토해야 한다.
15. **기존 결과 일괄 변환**: 과거 저장된 모든 검색 기록을 자동 마이그레이션하지 않았다. 기존 기록을 재검사하는 CLI는 실제 대상 페이지에 접속할 수 있으므로 단순 파일 변환과 구별한다.
16. **배포 검증**: 실제 SerpApi 인증·실검색 품질·과금량·오프라인 배포·EXE 재빌드·다른 Windows PC 검증은 아직 하지 않았다. 로컬 테스트 통과를 이 검증들로 확대 해석하지 않는다.

7. 사용자에게 바뀐 동작, 검증 범위, 아직 확인하지 못한 사항을 구분해 전달한다.
