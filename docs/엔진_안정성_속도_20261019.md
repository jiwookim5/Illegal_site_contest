# 점검 엔진 안정성과 탐색 속도 보고 (2026-10-19)

경상북도 누리집(gb.go.kr) 실제 점검 중 발견한 엔진 문제와 탐색 속도 개선을 정리한다. 판정 점수 변경은 `docs/점수_경계보정_20261019.md`와 `docs/오탐_미탐_조사와_개선방향_20261019.md`에 있다. 모든 변경은 소스 실행에만 반영됐고 `훤히.exe`는 다시 빌드하지 않았다. 커밋하지 않았다.

## 1. 페이지가 브라우저 기본 `Map`을 덮어쓸 때의 추출 실패

### 증상

gb.go.kr 점검이 183번째 페이지(`/gbsafe/main.tc`, 경상북도 재난안전대책본부)에서 '본문 확장 결과를 읽지 못했습니다'로 멈췄다. 결과 파일 없이 점검 전체가 실패했다.

### 원인

그 페이지의 라이브러리가 브라우저 기본 `Map`(그리고 `Object.keys`, `Date`)을 자기 구현으로 바꾼다. Playwright는 페이지 결과를 파이썬으로 돌려줄 때 페이지의 `Map`으로 순환 참조를 센다. 그래서 그 페이지에서는 객체·배열 결과가 모두 `None`이 됐다. 같은 페이지에서 `({a:1})`도 `None`이고, 기본 `Map`만 되돌리면 정상으로 돌아오는 것을 실제 페이지에서 확인했다.

같은 원인으로 우리 추출 스크립트의 `new Map()`도 페이지의 `Map`을 써서 실패했다(`inhCache.get is not a function`). 점검이 멈추지 않았더라도 그런 페이지의 글은 조용히 빈 채로 넘어가 광고를 놓쳤을 것이다.

### 수정 (`detector/browser.py`, `detector/session.py`)

- Playwright 내부 `Frame.evaluate`를 한 곳에서 감싼다. 페이지의 `Map`이 기본 구현이 아닐 때만 결과를 JSON 문자열로 받는다. 기본 구현이면 결과를 그대로 받으므로 평소 동작은 같다. 요소 핸들처럼 JSON으로 보낼 수 없는 인자는 원래 경로로 보낸다. 페이지 실행 호출 46곳에 함께 적용된다.
- 페이지 스크립트보다 먼저 도는 초기화 스크립트(`NATIVE_HOOK`)가 기본 `Map`·`Set`·`WeakMap`·`WeakSet`·`Date`를 잡아 두고, 감싼 스크립트 안에서 같은 이름으로 가려 그것을 쓰게 한다. `LAZY_HOOK`도 시작 시점의 `Map`·`WeakMap`을 쓴다.
- Playwright 1.63 내부 구조에 기대므로, Playwright를 올리면 `tools/test_page_builtin_overrides.py`를 다시 돌린다. 감쌀 수 없게 되면 그 시험의 첫 항목이 실패한다.

### 검증

- `tools/test_page_builtin_overrides.py` 6개 통과. 감싸기 전 소스로는 같은 시험 페이지에서 결과가 `None`이 되는 것을 확인했다(재현).
- 실제 `/gbsafe/main.tc` 한 쪽 재점검: 실패 없이 분석 완료, 검출 0건.

## 2. 페이지 하나의 오류가 점검 전체를 멈추지 않게 함 (`detector/scan.py`)

이전에는 한 페이지를 분석하다 예외가 나면 점검 전체가 실패했다. 이어서 점검해도 진행 중이던 페이지를 다시 열므로 같은 페이지에서 또 멈출 수 있었다.

- 페이지를 연 뒤 분석·탐색 구간의 예외는 그 페이지만 실패로 기록하고 다음 페이지로 넘어간다. 실패 사유는 기존 `fail_reason` 분류를 따르고, 다시 열어 볼 만한 실패는 한 번만 재시도한다. 재시도 한도를 넘긴 주소는 이어서 점검할 때도 다시 열지 않는다.
- 사용자 중단·시간 종료(`ScanStopped`)는 `BaseException`이라 잡히지 않는다. 진행 상태 저장 실패는 페이지 실패로 치지 않고 예전처럼 점검을 멈춘다.
- 잇달아 8쪽이 실패하면 기존 안전장치로 멈춘다. 이때 중단 사유가 `blocked`로 표시되어 차단과 구분되지 않는 점은 남은 과제다.
- 검증: `tools/test_page_builtin_overrides.py`의 `PageFailureIsolationTest`(실패 페이지 뒤 페이지도 끝까지 점검, 실패 기록에 원인 보존).

## 3. 이어서 점검 기능 점검

- 원인 여부: 1번 오류를 낸 코드는 이어서 점검 커밋(`15d9678`)보다 먼저(`4022603`) 들어왔다. 이어서 점검 기능이 원인이 아니다.
- 속도 영향: gb.go.kr 183쪽 실측에서 페이지 종료 시 저장이 모두 2.9초(쪽당 약 16ms), 페이지를 열기 전 저장은 단계 합계와 전체 시간의 차이로 보아 많아야 약 10초였다. 점검 시간의 약 1~2%다. 상태 전체를 매번 다시 쓰므로(183쪽에서 약 1MB) 수천 쪽 점검에서는 비율이 커질 수 있으나 측정하지 않았다.
- 재개 거절 조건: 탐지 코드 지문(`resume_state.engine_id`)은 `detector/*.py` 파일 바이트를 그대로 해시한다. 내용이 같아도 줄바꿈 형식(CRLF/LF)만 다르면 재개를 거절한다. 실제로 이 때문에 gb.go.kr 점검을 작업 폴더 소스로 이어 갈 수 없었다. 지문 계산 때 줄바꿈을 통일하는 수정이 남아 있다.
- CLI에는 재개 명령이 없다. gb.go.kr 2회차는 점검 시작 당시와 같은 바이트의 `detector` 사본을 임시 폴더에 만들고 지문 일치(`05140df…`)를 확인한 뒤, 앱의 '이어서 점검'과 같은 경로(`RunArchive.inherit` → `run_scan(resume_state=…)`)로 실행했다.

## 4. 탐색 속도: 자바스크립트 링크 찾기 (`detector/js_links.py`)

### 측정 근거

gb.go.kr 183쪽(약 781초) 단계별 시간에서 자바스크립트 링크 찾기(`discover.js`)가 403초로 절반이 넘었다. 페이지마다 이동 후보를 최대 60개까지 하나씩 누르고, 누를 때마다 브라우저 왕복과 40ms 대기가 있었다. 막지 못한 이동이 생기면 원래 페이지를 다시 불러왔다.

### 수정

- 후보를 한 번의 실행에서 차례로 누르고, 마지막에 150ms 한 번 기다린 뒤 기록을 읽는다(`BATCH_CLICK`). 이동은 원래부터 페이지 안에서 취소되고 목적지만 기록된다(`INSTALL_TRAP`).
- `form.submit()`의 이동은 다음 작업으로 미뤄지고 뒤의 전송이 덮어쓴다. 처음 구현은 '2쪽' 다음 바로 '3쪽'을 눌러 2쪽 주소를 놓쳤고, 기존 시험 `test_scan_speed_fixes`가 이를 잡았다. 누를 때마다 한 번 양보해 미뤄진 이동이 먼저 걸리게 고쳤다. 양보에는 `LAZY_HOOK`이 감싸기 전의 `setTimeout`을 써서 우리 대기를 페이지 타이머로 세지 않는다.
- 주소가 실제로 바뀌면 그 페이지만 원래 페이지로 돌아가 기존 방식(하나씩 누르기)으로 다시 한다.
- 계측: 결과의 `counts`에 눌러 본 후보 수(`discover.probes`), 한 번에 끝난 페이지(`discover.batch`), 하나씩 누르기로 되돌아간 페이지(`discover.fallback`), 다시 불러온 횟수(`discover.reload`)를 남긴다.

### 검증

- 정확도: 단위 시험 8종 통과. 로컬 시험 사이트 18곳의 주요·추가 검출 목록, 방문 페이지 수, 채점, 시험 서버가 받은 POST 기록이 같은 날 오전 실행(`_regress/runs/20261019-095539-f2eb1849`, `20261019-100104-c9a73b06`)과 모두 같다(`_regress/runs/20261019-180633-f8745a43`). 우회 시험 사이트 145/145, 함정 오탐 0/46(`_regress/batch-click-evasion.log`).
- 속도: **아직 측정하지 않았다.** 위 회귀는 gb.go.kr 점검과 동시에 가장 낮은 우선순위로 돌려 시간이 비교 대상이 아니다. 점검이 끝난 뒤 같은 조건에서 수정 전후를 비교한다.

## 5. 남은 속도 개선안

| 안 | 내용 | 상태 |
|---|---|---|
| 원래 페이지 다시 불러오기 줄이기 | 탭 전환 뒤 다시 열기(`discover.reopen`, 183쪽에서 28초)와 막지 못한 이동 뒤 재로딩 | 4번 계측의 `discover.reload`를 보고 결정 |
| 판정에 쓰지 않는 요청 막기 | 영상·분석 스크립트 등. 글꼴은 글꼴 바꿔치기 위장 탐지에 쓰므로 막지 않는다 | 미착수 |
| 진행 상태 저장 비용 | 페이지를 열기 전 저장을 가볍게 | 큰 점검에서 먼저 측정 |
| 여러 페이지 동시 점검 | 요청 간격을 탭끼리 나눠 지키면 서버 부담은 같게 두고 2~3배 | 공유 상태·재개 형식·결과 순서를 함께 바꿔야 해 별도 설계 |
