# 검색엔진 dork 보조 탐색 사용법

점검을 마친 결과 화면의 **추가 탐색하기**를 눌러 별도 단계에서 실행한다. 시작 화면에는 나오지 않는다. 대상 도메인은 점검 주소로 채운다. 광고단어는 사용자가 입력하지 않고, 공공 누리집에 실제로 노출된 불법광고 검색 결과에서 자주 보인 말을 유형별(도박·사행성, 도박 주소·계좌 거래, 대포통장·불법 대출, 마약·불법 의약품, 성인·유흥, 고수익 알바·가담자 모집, 외국어 도박 스팸)로 고정해 두었으며 검색할 유형만 고른다. 이번 점검에서 찾은 단어도 선택해 함께 검색할 수 있다. 고정 단어는 `detector/search_terms.py`에 있고 점검 사전에 있는 말만 쓴다. 화면 오른쪽 위 **검색 API** 표시에서 연결 상태를 확인한다. SerpApi는 계정 조회 API로 확인해 검색 호출량을 쓰지 않는다. 결과는 5분 동안 저장해 두고 [다시 확인]을 누를 때만 새로 묻는다. 키가 없으면 검색을 시작할 수 없다. 별도의 GUI 창은 만들지 않는다. CLI도 계속 사용할 수 있다. 소스 UI에 연결했으며 기존 배포 EXE는 아직 재빌드하지 않았다.

1. 점검 주소 가져오기를 누르거나 대상 도메인을 입력한다.
2. 검색할 광고 유형을 고른다. 검색엔진은 구글 하나다. 특정 단어를 더하려면 **고급: 검색 단어 직접 입력**을 펼쳐 한 줄에 하나씩 적는다. 고정 단어·찾은 단어·직접 입력 단어는 합쳐서 중복 없이 최대 30개까지 검색하며, 화면에 예상 최대 검색 횟수가 나온다.
3. 필요하면 접힌 **상세 설정**을 열어 키워드당 최대 페이지(UI 기본은 호출량을 고려해 2페이지)를 정한다.
4. 상세 설정에서 검색 범위를 고른다. 기본 **등록 도메인 전체(하위 도메인 포함)** 는 입력 주소의 등록 도메인(`www.example.go.kr` → `example.go.kr`)으로 `site:` 검색하고 그 하위 주소를 모두 결과에 넣는다. **입력한 주소만** 은 입력한 호스트로 검색하며, 이때만 나타나는 **입력한 주소 아래의 하위 도메인도 포함** 을 켜면 그 아래 주소까지 결과에 넣는다. 등록 도메인은 공개 접미사 목록 없이 `go.kr`·`co.kr` 같은 2단계 이름 규칙으로만 구한다.
5. 기본은 URL 수집만 한다. 대상 문서 검사까지 원하면 상세 설정의 **수집한 주소에 접속해 지금도 광고가 있는지 확인**을 선택한다.
6. 보조 탐색 시작을 누른다. 진행 막대와 지금 검색 중인 단어·페이지, **단어별 검색 상태**(상태·수집 URL 수)가 나온다. API 오류·시간 초과·대기 중처럼 결과를 받지 못한 질의는 **확인이 필요한 질의** 표에 단어·페이지·사유로 따로 보여 준다. 처리 기록(로그)은 접힌 칸에서 볼 수 있다. 검색 중지(검색 중에만), 대기 결과 회수(받을 결과가 있을 때만), 검색 보고서 열기가 같은 화면에서 필요할 때 나타난다.
7. **지난 검색 보기** 에서 출력 폴더 `search_results` 에 남은 지난 검색을 최근 것부터 고른다. 열면 그 검색의 수집 URL 수·보고서·제출 반영 건수가 현재 검색 자리에 나온다. 검색 중에는 열 수 없고, 새 검색을 시작하면 새 검색으로 바뀐다.

기본 탐지·조치 확인·검색 작업은 동시에 실행하지 않는다. 기본 탐지의 result.json과 실행 아카이브는 보존한다. 검색 파일은 기존 결과 저장 폴더 아래 search_results에 저장한다. 소스 실행 시 search.env는 hwonhi 폴더, EXE 실행 시 EXE 옆에 둔다. search_dorks.json이 없으면 기본 템플릿을 사용한다. 대기 결과 회수 버튼은 현재 프로그램 세션의 미완료 검색에 적용하며 재시작 후에는 CLI의 --resume-search로 저장 파일을 지정한다.

### 공모전 제출 JSON

검색 실행 폴더의 `result_extra.json`에 검색 제목·요약을 기존 광고 판정기로 확인한 결과를 `meta + findings` 형식으로 저장한다. `technique`은 `ETC`이며 `extra_finding`은 다음과 같다.

- `SEARCH_INDEXED_AD`: 검색 결과의 광고 노출. 현재 페이지 미검사·확인 불가·광고 미탐지·삭제 안내 의심은 근거에 별도 표시한다.
- `SEARCH_PARAMETER_AD`: 광고로 판정된 URL 파라미터가 있고 검색 제목·요약에도 광고가 노출된 경우. 반영 여부는 현재 상태와 함께 기록한다.
- `SEARCH_REMOVED_AD`: 검색에는 광고가 노출되지만 현재 URL은 HTTP 404·410 응답인 경우. 과거 게시글의 존재나 삭제 원인까지 증명하는 것은 아니다.
- `SEARCH_LIVE_AD`: 검색에 광고가 노출되고 현재 페이지 검사에서도 광고를 찾은 경우.

URL이나 검색어에 키워드가 있다는 이유만으로 제출 결과에 포함하지 않는다. `is_violation`은 검색 노출 광고에 대한 판정이며 현재 페이지의 광고 존재 여부와 구분한다. API 결과에 없는 CSS 선택자를 만들지 않고 `location`에 검색엔진·검색 URL·페이지·대상 링크를 기재한다. 검색 제목·요약 원문과 조회 시각, 현재 상태는 `evidence_text`에 남긴다. 정상·미확인 후보를 포함한 전체 수집 기록은 내부용 `results.json`에 보존한다.

GUI 검색·회수 완료 시 출력 폴더의 `result_extra.json`에도 병합한다. 기존 추가 검출은 보존하며 동일 검색 실행을 재검사·회수하면 그 실행의 항목만 교체한다. 기존 제출 파일과 대상 호스트(포트 포함)가 다르면 합치지 않고 검색 실행 폴더의 제출 JSON을 사용하도록 로그로 안내한다. 손상된 기존 파일은 덮어쓰지 않는다. CLI는 `--out` 검색 폴더의 부모에 병합하며, `--input`·`--resume-search` 사용 시에도 `--out`으로 검색 저장 루트를 지정한다.

합본의 `meta` 시간은 최초 점검부터 마지막 검색 종료까지의 경과 시간(사이의 대기 포함)이다. 적격평가용 `result.json`의 시간은 변경하지 않는다. 새 기본 점검이나 이력 전환으로 출력 폴더의 제출 사본이 교체될 수 있으며, 검색 실행 폴더의 `result_extra.json`은 계속 보존된다.

## API 발급과 설정

구글은 **SerpApi 키 하나**로 검색한다. 네이버·다음·카카오 검색은 지원하지 않는다. SerpApi는 검색엔진 운영사의 공식 API가 아닌 외부 검색결과 API 서비스다. 검색할 도메인과 질의어가 해당 서비스에 전달되며 계정의 호출량을 사용한다.

1. [SerpApi 가입](https://serpapi.com/users/sign_up) 후 계정에서 API 키를 확인한다. 요금·잔여 검색량은 해당 서비스의 현재 플랜을 확인한다.
2. 화면 오른쪽 위 **검색 API**를 눌러 **SerpApi API 키**에 발급받은 키를 입력한다.
3. **저장 및 연결 확인**을 누르면 `search.env`에 저장하고 연결 상태·잔여 검색량을 확인한다. 기존 키는 화면으로 내려보내지 않으며 등록 상태만 표시한다. **보기**는 방금 입력한 키만 표시하고 **키 삭제**는 저장된 키를 제거한다. 검색·점검 중에는 키를 변경할 수 없다. 환경변수 `SERPAPI_API_KEY`가 설정된 경우 환경변수가 우선하며 화면에서 변경할 수 없다. 환경변수를 해제하고 프로그램을 다시 실행하면 화면에서 설정할 수 있다.

   파일로 직접 설정하려면 `search.env.example`을 `search.env`로 복사하고 `SERPAPI_API_KEY=` 뒤에 키를 넣는다. 키는 로컬 파일에 평문으로 보관되므로 이 파일을 공유하지 않는다. 키를 채팅·소스·보고서에 넣지 않는다.
4. 기본 `hybrid` 모드로 실행한다. 검색엔진은 구글 API다. 검색 화면 수집이 필요하면 CLI의 `browser` 모드를 사용한다.

구글은 `engine=google`, `q`, `start`를 사용한다. [구글용 API 문서](https://serpapi.com/search-api). 구글 자체 Custom Search JSON API는 신규 고객에게 제공되지 않고 기존 고객도 2027년 1월 1일까지 전환해야 하므로 기본 경로로 채택하지 않았다. [구글 공식 안내](https://developers.google.com/custom-search/v1/overview).


## dork 템플릿


`search_dorks.json`에서 질의 템플릿 목록을 편집한다. `{domain}`과 `{term}`은 필수이며 기본은 `site:{domain} {term}`이다. 제목·경로 집중 탐색을 시험할 때 다음처럼 추가할 수 있다. 예전 설정 파일에 `naver` 항목이 남아 있어도 사용하지 않는다.

```json
{
  "google": ["site:{domain} {term}", "site:{domain} intitle:{term}", "site:{domain} inurl:search {term}"]
}
```

질의 도메인은 검색 범위에 따른다(위 4번). 기본은 등록 도메인이고, **입력한 주소만** 을 고르면 입력한 호스트 그대로 쓰며 `www.example.go.kr`과 `example.go.kr`을 합치지 않는다. 하위 도메인 포함 옵션은 결과 필터 범위를 넓힌다. 제출 파일(`result_extra.json`)의 `entry_url` 은 범위와 관계없이 입력한 주소로 적어 기본 점검 결과와 합쳐지게 한다. 원본 URL의 쿼리·중복 파라미터·인코딩·스킴을 보존하고 정확히 같은 URL만 통합한다. 제목·요약에 단어가 없더라도 대상 URL은 검사 후보에 남긴다.

검색은 단어 30개, 엔진당 템플릿 10개, 질의당 페이지 10개, 통합 URL 300개로 제한한다. 기본은 질의당 최대 5페이지다. API 오류 시 해당 질의의 페이지 탐색을 멈추고 다음 질의로 진행한다. API 키가 없어도 이를 성공 0건으로 표시하지 않는다. 검색 화면 방식은 Edge 설치가 필요하며 캡차·동의 화면·화면 구조 변화는 별도 상태로 기록한다. 자동 우회하지 않는다.

## 재검사와 결과

기존 `BrowserSession`의 페이지 열기·동적 영역 처리와 `walk_frame`, `classify` 판정을 재사용한다. 목록 URL을 직접 열어 본문과 iframe의 기본 탐지를 수행하며 전체 사이트를 다시 탐색하지 않는다. 첨부파일·OCR·크롤러 위장 비교는 이 보조 재검사에 포함하지 않는다. 원본 URL과 최종 URL을 별도로 보관한다. robots.txt, 상태 변경 링크 제외, 요청 간격을 적용한다.

- `광고 탐지`: 기존 탐지 함수의 근거를 저장한다.
- `파라미터 반영`: URL의 광고 후보 값이 현재 페이지에 나타난다. 정상 검색 문맥인지 검토가 필요하다.
- `파라미터 문구만 존재`: 후보 값이 URL에 있지만 현재 본문에서 같은 값이 확인되지 않는다.
- `삭제 응답`: HTTP 404·410. 검색 당시 노출과 현재 상태를 함께 검토한다.
- `삭제 안내 의심`: HTTP 200의 삭제 안내 문구. 실제 삭제 확정과 구분한다.
- `현재 광고 미탐지`: 현재 엔진이 찾지 못한 경우이며 안전 확정이 아니다.
- `확인 불가`: 차단·시간 초과·오류·부분 검사·범위 밖 이동 등이다.

`search_results/실행폴더/`에 `urls.txt`, `results.json`, `review.csv`, `report.html`을 저장한다. `report.html`은 점검 결과 보고서와 같은 양식(`detector/search_report.py`)이다. 인쇄·PDF 저장 단추, 요약 타일(수집 URL·광고로 판정·광고 문구가 주소에 포함·삭제 응답인데 노출·현재 페이지에도 광고), 검색 정보(범위·일시·소요·검색엔진), 중지·상한·확인 못 한 질의 안내, 판정 유형별 건수, 수집한 URL 목록(광고 판정 먼저, **광고 판정**·**검토 필요** 표시, 긴 주소는 도메인·경로를 굵게 하고 쿼리를 풀어 보여 주며 전체 주소는 접어 둠), 질의별 수집 상태, 결재란으로 구성된다. 각 엔진 폴더의 `search_evidence/`에는 API 증거 JSON 또는 검색 화면 PNG·HTML 텍스트가 있다. `page_evidence/`에는 검사 화면과 근거가 있다. API 증거는 인증 정보를 제외한 검색 ID·시각·결과 필드다. 검색 원문 전체 응답이나 실제 검색 화면 캡처와 동일한 자료라고 표시하지 않는다.

CSV는 검색 출처별로 행을 나눠 동일 URL의 엔진별 근거를 유지한다. JSON에는 개별 탐지 위치·기법도 남긴다. 담당자가 검토해 색인삭제 요청에 활용하는 자료이며 삭제 요청을 자동 전송하지 않는다. 중지 시 완료한 결과는 유지하고 나머지는 미검사로 남긴다. `--input 경로/results.json`으로 같은 결과 파일을 다시 검사할 수 있다.

## CLI

프로젝트 루트에서:

```powershell
.venv/Scripts/python.exe detector/search_assist.py --site example.go.kr --term 카지노 --term 꽁머니 --engines google --mode api --pages 2
```

`--collect-only`는 URL 수집만, `--mode browser`는 구글 검색 화면 수집, `--input 경로/results.json`은 저장 결과 재검사다. `--dorks`, `--keys`, `--out`으로 설정과 출력 위치를 바꿀 수 있다.

저장된 검색을 `--input`이나 `--resume-search`로 처리하면 제출 합본은 원래 출력 폴더의 `result_extra.json`에 저장한다. 표준 배치인 `<출력 폴더>/search_results/<검색 폴더>/results.json`과 그 아래 `google/results.json`을 모두 지원한다. 대상 URL 재검사는 같은 출력 폴더의 점검 제외 목록을 적용하며 검색에서 수집한 제목·요약은 보존한다.

2026년 10월 15일 실제 API로 구글 질의의 첫 페이지를 확인했다. `site:example.com example`은 3개, `site:namu.wiki 카지노`는 10개 URL을 반환했다. 결과 수는 검색 시점에 따라 달라진다. (같은 날 확인한 네이버 결과는 네이버 검색 기능을 제거하면서 이 문서에서 뺐다.)

구글 응답이 45초를 넘는 사례가 있어 API 대기 제한을 90초로 늘렸으며 시간 초과·네트워크 오류를 구분한다. 검증은 API 검색과 결과 저장까지만 수행했고 검색 대상 문서에는 접속하지 않았다. 파라미터 보존, URL 목록 일치, 근거 파일 연결, 결과 파일의 키 비노출도 확인했다. 다중 페이지 수집은 이번 실제 API 검증 범위에 포함하지 않았다.


## 비동기 검색과 미완료 결과 회수

구글 SerpApi 검색은 `async=true`로 한 번 제출하고 검색 ID를 즉시 저장한다. 이후 5초 간격으로 같은 ID의 Search Archive API를 조회한다. `no_cache`는 함께 사용하지 않는다. 개별 HTTP 요청의 제한은 90초이며 전체 처리 대기는 약 300초다(진행 중 HTTP 요청에 따라 초과할 수 있다).

대기 한도나 일시적 보관 조회 오류는 `pending`, 사용자 중지는 `cancelled`, 제공자의 최종 실패는 `error`다. 어느 경우도 정상 검색 0건으로 표시하지 않는다. 보고서에는 검색 ID·제공자 상태·대기 시간이 표시된다. 최초 제출 중 연결이 끊겨 ID를 받지 못하면 자동으로 재제출하지 않는다. 이 경우 계정 검색 기록을 확인해야 한다.

아래 CLI 명령으로 results.json을 지정해 저장된 미완료 검색만 다시 조회한다. 새 검색·다음 페이지 요청·대상 문서 재검사는 수행하지 않는다. 실행 중 강제 종료된 경우 엔진 하위 폴더의 results.json에 ID가 남아 있을 수 있다.

```powershell
.venv/Scripts/python.exe detector/search_assist.py --resume-search "결과폴더/results.json"
```

2026-10-15 비동기 방식으로 `site:www.gimhae.go.kr 가입머니`를 실제 재확인했다. 두 요청 모두 HTTP 503이었고, 두 번째 응답의 검색 ID는 `6ad0a5a9a2080247ce742395`, 제공자 상태는 `Error`였다. 제공자 메시지는 유효한 검색 결과를 얻지 못했다는 내용이었다. 따라서 URL 수집 성공이나 정상 무결과를 확인한 것은 아니다. 대상 김해시 페이지에는 접속하지 않았다.


## 여러 페이지·하위 링크 수집

API 모드의 기본 페이지 한도는 5, 설정 가능한 최대치는 10이다. 구글은 다음 페이지 정보가 없어도 `start=10,20,...`으로 추가 페이지를 확인한다. 정상 무결과, 동일 URL 집합 반복, API 오류·대기, 사용자 중지, 300개 URL 상한 또는 설정 페이지 한도에 도달하면 종료한다. 반복 페이지의 링크 순서만 달라져도 같은 집합으로 판별한다. 한 질의의 오류가 다음 키워드 검색을 막지 않는다.

SerpApi 일반 검색 결과의 대표 URL과 `sitelinks.inline`, `sitelinks.expanded` 하위 링크를 수집한다. 사이트 본문을 방문해서 링크를 확장하는 기능은 아니다. 하위 링크의 제목·요약·부모 URL·출처 유형을 저장하고 원본 파라미터를 보존한다. 검색 화면(browser) 방식의 추출 범위는 기존 방식과 같다.

보고서에 요청 페이지 수, 수신 링크 합계(중복 포함), 하위 링크 수, 최종 고유 URL 수를 표시한다. 페이지별로 대상 링크·신규 URL·범위 밖/유효하지 않은 링크·중복/상한 제외 수와 진행 또는 종료 이유를 표시한다. API 실패는 수신 수 미확인으로 표시하며 정상 무결과와 구분한다. 저장 ID 회수는 해당 페이지 결과만 가져오므로 추가 페이지 검색은 새 검색 실행이 필요하다.

2026-10-15 추가 검증: `site:www.gimhae.go.kr 먹튀검증`을 5페이지 검색해 수신 링크 45건, 고유 URL 40건을 저장했다. 하위 링크는 이번 응답에 없었다(0건). 종료 이유는 설정 페이지 한도 도달이다. `가입머니`는 API 연결 오류로 종료되어 정상 무결과로 판단할 수 없다. 결과 폴더: `search_results/www.gimhae.go.kr_20261015_195715_ca54c4/`.
